# Code Audit — DuaPrayer (2026-06-10)

Scope: `apps/dua-prayer` (Next.js 15 App Router + Supabase + Stripe, ~258 TS/TSX source files).
Method: security audit (server actions, API routes, RLS, webhooks), correctness audit (lib, actions, components), consistency/hygiene audit (config, deps, dead code). Critical findings verified by hand against source.

---

## Critical

### C1. Privilege escalation: any user can make themselves admin via RLS
`supabase/migrations/20250608000000_initial_schema.sql:176-177`

```sql
CREATE POLICY profiles_update_own ON public.profiles FOR UPDATE TO authenticated
  USING (id = auth.uid()) WITH CHECK (id = auth.uid());
```

The policy restricts *which rows* a user can update but not *which columns*. `is_admin`, `admin_role`, `admin_permissions`, `member_role`, and `account_status` all live on `profiles`. Any authenticated user can call the public anon-key Supabase client directly and run `update profiles set is_admin = true where id = auth.uid()`, bypassing every server-side permission check (which all derive from these columns).

**Fix:** column-level `REVOKE UPDATE (is_admin, admin_role, admin_permissions, member_role, account_status) ON public.profiles FROM authenticated;` (service role retains access), or a `BEFORE UPDATE` trigger that rejects changes to privileged columns unless the role is `service_role`. Ship as a new migration and apply to production immediately.

## High

### H1. Open redirect via `next` parameter
`app/auth/callback/route.ts:43-48`, `app/actions/auth.ts:36`

`new URL(next, requestUrl.origin)` and `redirect(next)` both accept absolute URLs — a crafted magic-link/sign-in URL with `?next=https://evil.com` redirects the freshly authenticated user off-site (phishing vector).
**Fix:** accept `next` only if it starts with a single `/` (reject `//` and absolute URLs); fall back to `/`.

### H2. Checkout endpoint unprotected against abuse
`app/api/checkout/route.ts:16`

Creates real Stripe Checkout Sessions for unauthenticated callers with no rate limit, no Turnstile, no honeypot — enables session-spam and card-testing abuse. (Amount is correctly bounded $1–$10,000.)
**Fix:** apply `checkRateLimit("checkout:" + ip, ...)` and Turnstile, mirroring `createDua` (`app/actions/duas.ts:296-307`).

### H3. Home feed silently capped at 100 duas
`app/actions/duas.ts:262` (`FEED_BATCH_SIZE = 100`), `components/feed-section.tsx:131-137`

`getFeedDuas` fetches only the newest 100 rows and the client paginates that array; once >100 published duas exist, older duas become unreachable. The properly server-paginated `getDuas()` exists but is never called. Right-rail stats (`app/page.tsx:71-80`) computed from the same 100-row slice will also undercount.
**Fix:** wire pagination to server-side `getDuas` (use real `count` for total); compute right-rail ameens from `getPlatformStats`.

### H4. Anonymous flagging via service-role client + fake "Unflag"
`app/actions/duas.ts:365-383`, `components/dua-list.tsx:170-176, 206`

Any visitor can flag any dua id (service-role client, no auth, no existence check). The "Unflag" button only flips local state — the DB row stays flagged.
**Fix:** validate the dua exists/is published; make unflag admin-only or remove the affordance; consider per-IP flag tracking.

## What's done right (keep it this way)

- Every mutating admin server action gates with `requirePermission`/`getAdminContext` before touching the service-role client.
- Founder protection in role/user actions; founder identity is env-driven, never client-trusted.
- Dua submission layers IP rate limit + honeypot + Turnstile.
- No secrets in `NEXT_PUBLIC_*`; admin UI exposes only key `last4`.
- Webhooks fail closed (503) when no secret configured.
- Stripe amount math (cents) is correct; no `redirect()` swallowed in try/catch; schema is versioned in 8 migrations.
- No XSS sinks found (only `dangerouslySetInnerHTML` is shadcn chart theming, not user input).
